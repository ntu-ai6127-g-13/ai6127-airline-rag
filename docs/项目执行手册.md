# 第一部分：先搞懂我们在做什么

## 1. 用大白话说，我们要做个什么东西

假设你要订一张新加坡飞伦敦的机票，想知道**哪家航空公司的经济舱腿部空间比较宽敞**。

现在你只能一条条翻网上的评论，翻几百条也未必看得全。

**我们要做的，就是一个能替你翻完这几万条评论、然后给你答案的工具。**

你输入：

```
新加坡飞伦敦，经济舱，哪家航司腿部空间评价最好？
```

它输出：

```
按座位舒适度排序（长途经济舱，共找到 412 条相关评论）

  Airline X    68% 的人给好评    "plenty of legroom even at the back"
  Airline Y    41% 的人给好评    "seat pitch acceptable but nothing special"
  Airline Z    22% 的人给好评    "cramped, knees against the seat in front"

顺便告诉你其他方面：
  客舱服务最好的是 Airline Z（74% 好评）
  性价比最高的是 Airline Y（63% 好评）

⚠ 每一条结论都能点开，看到支撑它的全部原始评论
```

**最后那句话是关键。** 它不是凭空生成一段话给你，而是**每句结论都能追溯到真实的评论原文**。你可以自己点开核对。

## 2. 这个东西是怎么运转的

整个系统分两大块：**一块是提前准备好的，一块是你提问时才跑的。**

### 第一块：提前准备（只做一次）

```
   13.2 万行的 Excel 表（其中一半是空行）
            ↓
   ① 清洗：删掉重复的、空的，把航司名字统一
            ↓
   ② 切句：把每条评论拆成一句一句
            ↓
   ③ 建索引：做两套"目录"，方便快速查找
            ↓
   存起来，以后每次查询直接用
```

**为什么要切句？** 因为一条评论常常同时夸一个方面、骂另一个方面：

> "The seat was comfortable but the food was terrible."
> （座位很舒服，但飞机餐很难吃）

如果整条评论只打一个标签，这句话到底算好评还是差评？说不清。
**拆成两句分别处理，就清楚了**：座位 = 好评，餐饮 = 差评。

**什么是"索引"？** 就像一本书后面的索引页。没有索引，你想查"贝叶斯"这个词，
得从第一页翻到最后一页；有了索引，直接翻到第 237 页。

我们要建**两套**索引，原因见下一节。

### 第二块：你提问时才跑的

```
   你的问题
      ↓
   ① 看懂你的约束条件（哪家航司？什么舱位？什么时间段？关心哪个方面？）
      ↓
   ② 用两种方式各找一遍，再把结果合并
      ↓
   ③ 从合并结果里挑出最相关的十几条
      ↓
   ④ 判断每条是好评还是差评，属于哪个方面
      ↓
   ⑤ 统计比例，生成对比结论，附上原文
      ↓
   显示在网页界面上
```

## 3. 为什么要"两种方式各找一遍"

这是整个项目的技术核心，值得讲清楚。

### 方式一：关键词检索（按字面找）

就是**加强版的 Ctrl+F**。你搜 `legroom`，它就找出所有含 `legroom` 这个词的句子。

- ✅ **优点：精确。** 搜 `Airline X` 一定能找到提到 Airline X 的句子
- ❌ **缺点：不认同义词。** 搜 `legroom`（腿部空间），
  找不到只写了 `seat pitch`（座椅间距）或 `knee space`（膝盖空间）的句子——
  **但它们说的是同一件事**

### 方式二：语义检索（按意思找）

把每句话**变成一串数字**，意思相近的句子，数字也相近。

举个直观的例子。假设我们只用两个数字来表示一句话：

```
"腿部空间很大"        → (0.9, 0.2)
"座椅间距很宽敞"      → (0.87, 0.25)   ← 数字很接近，因为意思接近
"飞机餐很难吃"        → (0.1, 0.8)     ← 数字差很远，因为讲的是别的事
```

实际用的不是 2 个数字，而是 **384 个数字**。数字越多，能表达的语义差别越细。

- ✅ **优点：认同义词和换个说法。** 搜"腿部空间"能找到"座椅间距"
- ❌ **缺点：可能漏掉精确的专有名词。** 搜 `Airline X` 时，
  它可能返回一堆关于其他航司的句子，因为"航司名"这个概念太相似了

### 所以：两个都做，然后合并

**两种方式的优缺点正好互补。** 作业也硬性要求两种都实现，再合并成一套。

合并的方法叫 **RRF**，下一节讲。

## 4. 数据相关

**语料库 / 知识库（corpus / knowledge base）**
就是我们收集来的那 6.1 万条评论。系统只会从这些评论里找答案，不会自己编。

**chunk（切段后的一小块）**
把长文本切开后的每一小块。我们的 chunk = **一个句子**。
6.1 万条评论切完大约 54.6 万个句子。

**parquet（一种文件格式）**
可以理解成"**加强版的 csv**"。同样的数据，parquet 文件更小、读取更快。
用 pandas 读写只是把 `read_csv` 换成 `read_parquet`，用法几乎一样。

**元数据（metadata）**
除了评论正文以外的那些附加信息：航司名、日期、舱位、航线、各项评分。
**这些信息很值钱**，能让用户做"只看 2023 年之后的经济舱评论"这类精确筛选。

## 5. 检索相关

**BM25**
关键词检索用的一个经典公式。它给每个词算一个"重要程度"：

- 一个词在这句话里出现越多次 → 越可能相关
- 但这个词如果在所有句子里都出现（比如 `the`、`flight`）→ 说明它不特别，降权
- 句子太长的话适当降权，避免长句子占便宜

**你不需要自己推导这个公式**，有现成的库。但报告里要能讲清楚上面这三条直觉。

**embedding（向量 / 嵌入）**
就是第 3 节说的"把一句话变成一串数字"。这串数字就叫 embedding。

**FAISS**
一个专门用来**快速找最接近的向量**的工具库（Facebook 开发的）。
30 万个向量，一条条比对会很慢，FAISS 能在毫秒级找出最接近的几十个。

**RRF（倒数排名融合）**
把两份排好序的结果合并成一份的方法。核心思路：**只看排名，不看分数。**

```
关键词检索的结果：  [句子A, 句子B, 句子C]     ← A 排第 1
语义检索的结果：    [句子C, 句子A, 句子D]     ← A 排第 2

给每个句子算分：排第 n 名就得 1/(60+n) 分，两边的分数加起来
  句子A = 1/61 + 1/62 = 0.0325   ← 两边都靠前，总分最高
  句子C = 1/63 + 1/61 = 0.0323
  句子B = 1/62        = 0.0161
  句子D = 1/63        = 0.0159

最终排序：A > C > B > D
```

**为什么不直接把两边的分数加起来？**
因为 BM25 的分数可能是 12.7，语义相似度是 0.83——**量纲完全不同，加起来没有意义**。
而"排第几名"是两边都有的、可比的。

> 上面这段解释**可以直接写进报告**，是个不错的方法论说明。

**重排序（re-ranking）与 cross-encoder**
先用快的方法从 30 万句里粗筛出 100 条，**再用一个更慢但更准的模型**，
把这 100 条重新排一遍，挑出最好的 20 条。

那个"更准的模型"叫 **cross-encoder**。它和语义检索的区别是：

- 语义检索：把问题和句子**分别**变成数字，再比较——快，但比较粗糙
- cross-encoder：把问题和句子**放在一起**读，判断相关程度——准，但慢得多

所以只对粗筛出的 100 条用它，不对全部 30 万条用。

**parent-document retrieval（父文档回溯）**
我们检索的单位是句子，但只给用户看一个句子会缺上下文。
所以**检索命中句子，展示时把它所属的整条评论一起显示出来**。
这是作业点名的一个加分项。

## 6. 分类相关

**主观性判断（subjectivity detection）**
判断一句话是**陈述事实**还是**表达观点**。

- "The flight departed at 9am." → 客观事实
- "The seat was uncomfortable." → 主观评价

**极性判断（polarity detection）**
对上一步判定为"主观"的句子，判断是**好评还是差评**。

> **作业硬性要求这两步都做，不能跳过第一步直接分好评/差评。**

**方面（aspect）**
这句话在讲哪个方面。我们用数据自带的六个：
座位舒适度、客舱服务、餐饮、娱乐系统、地勤服务、性价比。

**弱标签（weak label）与远程监督（distant supervision）**

我们需要大量"这句话是好评还是差评"的训练数据，但人工标注很贵。

**好在数据里已经藏着答案**：每条评论，乘客给**六个方面**分别打了 1–5 星（不是每条都打满）。

```
某条评论，乘客给"座位"打了 5 星
  → 这条评论里讲座位的句子，大概率是好评      ← 这就是"弱标签"

某条评论，乘客给"餐饮"打了 1 星
  → 这条评论里讲餐饮的句子，大概率是差评
```

**为什么叫"弱"**：因为不完全准。评分是给整条评论的，而句子是一句一句的，
中间的对应关系有误差。但**量大**——约 **24.9 万条**免费的训练信号。

**这套"用现成的、不完美的标签来训练"的做法，学名叫 distant supervision（远程监督）**，
是真实研究里常用的方法。写进报告很有分量。

**金标准（gold standard）**
我们**人工精标的那 1,000 句**。用来**最终评测**，不参与训练。

> **必须分清楚**：弱标签用来**训练**，金标准用来**评测**。
> 两者混用会让评测结果失去意义。

## 7. 评测相关

**Precision@10（前 10 条的准确率）**
搜出来的前 10 条里，有几条是真正相关的。7 条相关 → 70%。

**Recall@50（前 50 条的召回率）**
全库总共有 20 条相关的，前 50 条里捞到了 14 条 → 70%。

> 一句话区分：**Precision 问"搜出来的准不准"，Recall 问"该搜到的漏没漏"。**

**MRR（平均倒数排名）**
第一条正确答案排在第几位。排第 1 得 1 分，排第 2 得 0.5 分，排第 3 得 0.33 分。
衡量的是"**用户要不要往下翻很久才能看到有用的东西**"。

**NDCG**
不只看搜得对不对，**还看排序好不好**——最相关的应该排最前面。

**faithfulness（忠实度）**
生成的答案里，**每句话是不是真的在检索到的原文里有依据**。
这是 RAG 系统最核心的指标——没有它，就退化成一个会瞎编的聊天机器人。

**消融实验（ablation study）**
做了多个改进时，**逐个关掉看各自贡献多少**。

```
只用关键词检索                 → 准确率 52%
只用语义检索                   → 准确率 58%
两个合并                       → 准确率 66%   ← 合并贡献了 8 个点
两个合并 + 重排序              → 准确率 71%   ← 重排序贡献了 5 个点
```

**作业硬性要求**：加了多个改进就必须这样逐个报告，不能只报"全都加上的效果"。

## 10. 三个组之间怎么交接 ★ 最关键的约定

### 10.1 `chunks.parquet` 的格式（全组共同遵守）

> 💡 **只是想用数据、不关心怎么建的**，直接看
> [`docs/数据使用指南.md`](数据使用指南.md)——那份是写给使用者的，
> 有读取方式、常见坑和各组的现成配方。本节是契约定义，偏规范。

| 列名 | 类型 | 说明 |
|---|---|---|
| `chunk_id` | 文本 | 这句话的唯一编号，如 `R48213_s03`（第 48213 条评论的第 3 句） |
| `review_id` | 文本 | 它属于哪条评论，用来回溯上下文 |
| `text` | 文本 | **句子原文** ← 检索和分类都是对它操作 |
| `review_text` | 文本 | 完整评论原文，展示证据时用 |
| `airline` | 文本 | 航司名 |
| `cabin` | 文本 | Economy / Premium Economy / Business / First |
| `traveller_type` | 文本 | 旅客类型：Solo / Couple / Family Leisure、Business |
| `aircraft` | 文本 | 机型，如 `A380`、`Boeing 777-300ER`（覆盖 30.2%，2,088 种） |
| `route` | 文本 | 航线原文，如 `Singapore to London via Dubai` |
| `route_from` | 文本 | **出发地**，从 route 拆出来的（99.7% 能拆开，拆不开为空） |
| `route_to` | 文本 | **目的地** |
| `route_via` | 文本 | **中转地**，没有中转为空 |
| `date` | 日期 | **评论**日期（覆盖 100%） |
| `date_flown` | 日期 | **实际乘机**月份（覆盖 61.2%，⚠️ **只有月精度**，日一律为 1） |
| `sent_idx` | 整数 | 这句在评论里的序号。⚠️ **不连续**（碎片句被丢过），别拿它判断末句 |
| `n_sents` | 整数 | 这条评论一共留下几句 |
| `n_words` | 整数 | 这句有几个词 |
| `is_last` | 真假 | 是不是本条评论的最后一句（末句常是总结句，是有用信号） |
| `is_route_only` | 真假 | 整句就是航线元数据（占 3.03%）。**建索引时建议 `WHERE NOT is_route_only`** |
| `dup_count` | 整数 | 这句话在全语料出现几次。**检索后建议按 text 去重**，否则 top-K 会被同一句占满 |
| `overall_rating` | 整数 | 总体评分 1–10 |
| `recommended` | 文本 | `yes` / `no`，该乘客是否推荐这家航司 |
| `r_seat` | 小数 | 座位舒适度 1–5 ★ 弱标签来源 |
| `r_staff` | 小数 | 客舱服务 |
| `r_food` | 小数 | 餐饮 |
| `r_entertainment` | 小数 | 娱乐系统 |
| `r_ground` | 小数 | 地勤服务 |
| `r_value` | 小数 | 性价比 |

一共 **28 列**。

> | v1 | `route_from/to/via` | 范例问题「新加坡飞伦敦」本质是按起降点过滤。在整条 `route` 里模糊匹配 `London` 会把 `London to Dubai`（从伦敦**出发**）也算成目的地，是错的 |

> | v3 | `sent_idx`、`n_sents`、`n_words`、`is_last`、`is_route_only`、`dup_count` | 结构列让「取上下文窗口」变成一个窗口函数；两个质量标记让检索能排掉 5.65% 的噪声 |
>
> 同一轮里还修了一个**静默 bug**：`date` 的覆盖率从 78.4% 修到 **100%**
> （原因见发现记录 B7，`pd.to_datetime` 认不了 `1st/2nd/3rd`）。

```python
import pandas as pd

df = pd.read_excel("data/raw/capstone_airline_reviews3.xlsx")

# ① 删掉全空的填充行（占一半！）和过短的正文

# ② 删掉完全重复的评论
before = len(df)
df = df.drop_duplicates(subset=["customer_review"])
print(f"去重删掉了 {before - len(df)} 条")

# ③ 航司名归一化（同一家可能有多种写法）
def clean_airline(name):
    if pd.isna(name):
        return None
    return name.strip().title()          # 去空格、统一大小写

df["airline"] = df["airline"].apply(clean_airline)
print("航司数量：", df["airline"].nunique())
print(df["airline"].value_counts().head(20))   # 看看有没有明显该合并的

# ④ 日期解析
df["review_date"] = pd.to_datetime(df["review_date"], errors="coerce")

# ⑤ 存起来
df.to_parquet("data/processed/reviews.parquet")
print("清洗完成，剩余", len(df), "条")
```

### 14.1 排序请用 `sent_idx`，不要用 `chunk_id` ⚠️

`chunk_id` 的格式是 `R000123_s07`，句序部分用了 2 位补零。
**句序超过 99 时会变成 3 位**（`_s100`），于是字典序就乱了——
`_s100` 会排在 `_s99` **前面**。

实测只有 1 条评论受影响（R041595，124 句），共 95 行。但要养成习惯：

```python
df.sort_values(["review_id", "sent_idx"])          # ✅ 正确
df.sort_values("chunk_id")                          # ❌ 长评论会乱序
```

```sql
ORDER BY review_id, sent_idx                        -- ✅
ORDER BY chunk_id                                   -- ❌
```

`chunk_id` 是**标识符**，不是排序键。要顺序就用 `sent_idx`——
这也正是加这一列的原因之一。

## 18. 第一步：关键词检索（BM25）

```python
# src/retriever.py
import pandas as pd, pickle
from rank_bm25 import BM25Okapi
from pathlib import Path

def build_bm25(chunks_path="data/processed/chunks.parquet"):
    df = pd.read_parquet(chunks_path)

    # 把每句话拆成词的列表（BM25 需要这种格式）
    tokenized = [t.lower().split() for t in df["text"]]

    bm25 = BM25Okapi(tokenized)

    Path("index").mkdir(exist_ok=True)
    with open("index/bm25.pkl", "wb") as f:
        pickle.dump({"bm25": bm25, "chunk_ids": df["chunk_id"].tolist()}, f)
    print("BM25 索引建好了，覆盖", len(df), "个句子")


def search_bm25(query, top_k=100):
    with open("index/bm25.pkl", "rb") as f:
        d = pickle.load(f)
    scores = d["bm25"].get_scores(query.lower().split())
    # 取分数最高的 top_k 个
    top_idx = scores.argsort()[::-1][:top_k]
    return [(d["chunk_ids"][i], float(scores[i])) for i in top_idx]
```

**验证它能用**：

```python
build_bm25("data/processed/chunks_sample.parquet")   # 先用抽样数据试
for cid, score in search_bm25("legroom seat", top_k=5):
    print(f"{score:.3f}  {cid}")
```

> ⚠️ **注意**：这里用 `split()` 简单分词就够了。
> 如果想做得更好，可以加**去停用词**（去掉 the、a、is 这些没信息量的词）
> 和**词形还原**（把 seats 还原成 seat）——**这两个可以作为改进点写进报告的 Q3**。

## 19. 第二步：语义检索（向量）

分两步：先把所有句子变成向量存起来，再用 FAISS 快速查找。

```python
# src/retriever.py 续
import numpy as np, faiss
from sentence_transformers import SentenceTransformer

MODEL_NAME = "all-MiniLM-L6-v2"   # 小而快，CPU 也能跑

def build_faiss(chunks_path="data/processed/chunks.parquet"):
    df = pd.read_parquet(chunks_path)
    model = SentenceTransformer(MODEL_NAME)

    # 把所有句子变成向量。show_progress_bar 让你知道跑到哪了
    embeddings = model.encode(
        df["text"].tolist(),
        batch_size=64,
        show_progress_bar=True,
        normalize_embeddings=True,      # 归一化后，内积就等于余弦相似度
    )

    # 建 FAISS 索引。IndexFlatIP = 用内积做暴力搜索，30 万条完全够用
    index = faiss.IndexFlatIP(embeddings.shape[1])
    index.add(embeddings.astype("float32"))

    faiss.write_index(index, "index/faiss.index")
    np.save("index/chunk_ids.npy", df["chunk_id"].values)
    print("向量索引建好了，维度", embeddings.shape)


def search_dense(query, top_k=100):
    model = SentenceTransformer(MODEL_NAME)
    index = faiss.read_index("index/faiss.index")
    chunk_ids = np.load("index/chunk_ids.npy", allow_pickle=True)

    q_vec = model.encode([query], normalize_embeddings=True).astype("float32")
    scores, idx = index.search(q_vec, top_k)
    return [(chunk_ids[i], float(s)) for i, s in zip(idx[0], scores[0])]
```

> ⏱ **时间提示**：30 万句用 MiniLM 在普通笔记本 CPU 上编码，
> **大约 1–2 小时**。跑一次存下来就行，不用反复跑。
> 想先快速验证流程，可以先只编码 5 万句。

> 💡 **加载模型很慢**，别在每次查询里都 `SentenceTransformer(...)`。
> 正式代码里把 model 和 index 加载一次存成全局变量。

## 20. 第三步：把两种检索合并（RRF）

```python
def rrf_fuse(list_a, list_b, k=60, top_k=50):
    """
    list_a, list_b: [(chunk_id, score), ...] 已按分数从高到低排好
    k=60 是论文里的经验值，不用改
    """
    scores = {}
    for lst in (list_a, list_b):
        for rank, (cid, _) in enumerate(lst, start=1):
            scores[cid] = scores.get(cid, 0.0) + 1.0 / (k + rank)

    ranked = sorted(scores.items(), key=lambda x: x[1], reverse=True)
    return ranked[:top_k]


def search_hybrid(query, top_k=50):
    a = search_bm25(query, top_k=100)
    b = search_dense(query, top_k=100)
    return rrf_fuse(a, b, top_k=top_k)
```

**就这么几行。** 简单是它的优点——好实现、好解释、效果稳。

## 21. 第四步：按元数据筛选

用户说"只看经济舱"或"只看 2023 年之后"时，要能过滤。

```python
def search_with_filters(query, filters=None, top_k=50):
    """
    filters 例子：{"cabin": "Economy", "airline": ["Airline X", "Airline Y"],
                   "date_from": "2023-01-01"}
    """
    df = pd.read_parquet("data/processed/chunks.parquet")

    # 先算出哪些 chunk 满足条件
    mask = pd.Series(True, index=df.index)
    if filters:
        if "cabin" in filters:
            mask &= df["cabin"] == filters["cabin"]
        if "airline" in filters:
            mask &= df["airline"].isin(filters["airline"])
        if "date_from" in filters:
            mask &= df["date"] >= pd.Timestamp(filters["date_from"])
    allowed = set(df.loc[mask, "chunk_id"])

    # 多取一些候选，因为过滤会砍掉一部分
    results = search_hybrid(query, top_k=top_k * 5)
    return [(cid, s) for cid, s in results if cid in allowed][:top_k]
```

> **这是"先检索后过滤"的做法**，实现简单。
> 如果过滤条件很严格（比如只有一家航司），可能过滤完就剩几条了——
> 这时候要把 `top_k * 5` 调大。**这个权衡本身可以写进报告。**

```python
# src/rerank.py
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

def rerank(query, candidates, chunks_df, top_k=20):
    """candidates: [(chunk_id, score), ...] 通常传 100 条进来"""
    id2text = dict(zip(chunks_df["chunk_id"], chunks_df["text"]))
    pairs = [(query, id2text[cid]) for cid, _ in candidates if cid in id2text]
    ids   = [cid for cid, _ in candidates if cid in id2text]

    scores = reranker.predict(pairs)          # 给每个 (问题, 句子) 打分
    ranked = sorted(zip(ids, scores), key=lambda x: x[1], reverse=True)
    return ranked[:top_k]
```

### 然后算这四个指标

```python
import numpy as np

def precision_at_k(relevances, k):
    """relevances: 按检索排序的 [1,0,1,1,0,...]"""
    return sum(relevances[:k]) / k

def recall_at_k(relevances, k, total_relevant):
    return sum(relevances[:k]) / total_relevant if total_relevant else 0

def mrr(relevances):
    for i, r in enumerate(relevances, start=1):
        if r == 1:
            return 1.0 / i          # 第一条正确答案在第 i 位
    return 0.0

def ndcg_at_k(relevances, k):
    rel = np.array(relevances[:k])
    # DCG：排得越靠前，贡献越大
    dcg = np.sum(rel / np.log2(np.arange(2, len(rel) + 2)))
    # IDCG：理想情况（所有相关的都排最前面）
    ideal = np.sort(np.array(relevances))[::-1][:k]
    idcg = np.sum(ideal / np.log2(np.arange(2, len(ideal) + 2)))
    return dcg / idcg if idcg > 0 else 0.0
```

## 26. 第一步：从评分造弱标签 ★ 本项目最有分量的一步

回顾第 6 节：数据里每条评论有**六个**方面的 1–5 星评分（稀疏，不是每条都打满）。
我们要**把这些评分变成句子级的训练标签**。

```python
# src/weak_labels.py
import pandas as pd

# 每个方面对应哪一列评分，以及判断这句话是否在讲该方面的关键词
# ⚠️ 只有 6 个维度，没有 wifi。完整定义见 src/config.py
ASPECT_CONFIG = {
    "seat":          ("r_seat",  ["seat", "legroom", "leg room", "pitch",
                                  "recline", "cramped", "comfortable"]),
    "staff":         ("r_staff", ["crew", "staff", "attendant", "service",
                                  "stewardess", "friendly", "rude"]),
    "food":          ("r_food",  ["food", "meal", "drink", "breakfast",
                                  "dinner", "snack", "catering"]),
    "entertainment": ("r_entertainment", ["entertainment", "movie", "screen",
                                          "ife", "film", "tv"]),
    "ground":        ("r_ground", ["check-in", "checkin", "boarding", "gate",
                                   "luggage", "baggage", "ground"]),
    "value":         ("r_value", ["value", "price", "expensive", "cheap",
                                  "worth", "money"]),
}


def make_weak_labels(chunks_path="data/processed/chunks.parquet"):
    df = pd.read_parquet(chunks_path)
    rows = []

    for _, r in df.iterrows():
        text_low = r["text"].lower()

        for aspect, (rating_col, keywords) in ASPECT_CONFIG.items():
            # 这句话提到该方面的关键词了吗？
            if not any(kw in text_low for kw in keywords):
                continue

            score = r.get(rating_col)
            if pd.isna(score):
                continue

            # 4-5 星 → 好评；1-2 星 → 差评；3 星模糊，丢掉
            if score >= 4:
                polarity = "positive"
            elif score <= 2:
                polarity = "negative"
            else:
                continue

            rows.append({
                "chunk_id": r["chunk_id"],
                "text": r["text"],
                "aspect": aspect,
                "polarity": polarity,
                "source": "weak",
            })
            break        # 一句话只归一个方面，取第一个匹配到的

    out = pd.DataFrame(rows)
    out.to_parquet("data/processed/weak_labels.parquet")
    print(f"造出 {len(out)} 条弱标签")
    print(out["aspect"].value_counts())
    print(out["polarity"].value_counts())
    return out
```

### 这一步必须诚实面对的三个问题

**写进报告是加分项**，掩盖反而扣分：

| 问题 | 为什么是问题 | 怎么处理 |
|---|---|---|
| **评分是给整条评论的，标签却用在句子上** | 一条评论给座位打 5 星，但里面某句可能在说"虽然座位不错，但..." | 只给**明确提到该方面关键词**的句子打标签，其余不参与训练 |
| **关键词匹配不完美** | 有些句子讲座位但没用到我们列的词 | 如实说明这是简化处理；可以在报告里作为"未来改进方向" |
| **丢掉 3 星会引入偏差** | 中间地带的样本全没了，模型可能过于"非黑即白" | **报告里说明丢弃了多少比例**，并在金标准上评测时观察这个影响 |

```python
# src/train_classifier.py
import pandas as pd, numpy as np
from datasets import Dataset
from transformers import (AutoTokenizer, AutoModelForSequenceClassification,
                          TrainingArguments, Trainer)
from sklearn.metrics import precision_recall_fscore_support, accuracy_score

MODEL = "distilbert-base-uncased"

def train_polarity():
    df = pd.read_parquet("data/processed/weak_labels.parquet")
    df["label"] = (df["polarity"] == "positive").astype(int)

    ds = Dataset.from_pandas(df[["text", "label"]]).train_test_split(test_size=0.1)
    tok = AutoTokenizer.from_pretrained(MODEL)

    def tokenize(batch):
        return tok(batch["text"], truncation=True, max_length=128)

    ds = ds.map(tokenize, batched=True)

    model = AutoModelForSequenceClassification.from_pretrained(MODEL, num_labels=2)

    def metrics(pred):
        labels = pred.label_ids
        preds = pred.predictions.argmax(-1)
        p, r, f1, _ = precision_recall_fscore_support(labels, preds, average="binary")
        return {"accuracy": accuracy_score(labels, preds),
                "precision": p, "recall": r, "f1": f1}

    args = TrainingArguments(
        output_dir="models/polarity",
        num_train_epochs=2,
        per_device_train_batch_size=32,
        eval_strategy="epoch",
        save_strategy="epoch",
        load_best_model_at_end=True,
        logging_steps=100,
    )

    trainer = Trainer(model=model, args=args,
                      train_dataset=ds["train"], eval_dataset=ds["test"],
                      compute_metrics=metrics)
    trainer.train()
    trainer.save_model("models/polarity")
```

## 30. 第五步：生成模块

拿到检索结果和分类结果后，**汇总成给用户看的答案**。

```python
# src/generate.py
import pandas as pd
from collections import defaultdict

def aggregate(results, predictions_df, chunks_df):
    """把检索到的句子按 航司×方面 汇总成比例"""
    stats = defaultdict(lambda: {"pos": 0, "neg": 0, "examples": []})

    for cid, _ in results:
        pred = predictions_df[predictions_df["chunk_id"] == cid]
        if pred.empty or pred.iloc[0]["subjectivity"] != "subjective":
            continue
        p = pred.iloc[0]
        row = chunks_df[chunks_df["chunk_id"] == cid].iloc[0]
        key = (row["airline"], p["aspect"])

        stats[key]["pos" if p["polarity"] == "positive" else "neg"] += 1
        if len(stats[key]["examples"]) < 3:
            stats[key]["examples"].append({"text": row["text"], "chunk_id": cid})

    out = []
    for (airline, aspect), s in stats.items():
        total = s["pos"] + s["neg"]
        if total < 5:            # 样本太少不下结论
            continue
        out.append({"airline": airline, "aspect": aspect,
                    "positive_rate": s["pos"] / total, "n": total,
                    "examples": s["examples"]})
    return sorted(out, key=lambda x: x["positive_rate"], reverse=True)
```

### ⚠️ 两条铁律

**① 比例必须用代码算，不要让大模型算。**
大模型数数不可靠，让它数"有几条正面"会出错。**代码算准确率，模型只负责组织语言。**

**② prompt 里必须限定只能用给定材料。**

# 第八部分：怎么协作

## 36. 分工

作业允许拆成三个小组，正好对应三块分：

| 小组 | 人数 | 分值 | 负责 | 自己写的报告部分 |
|---|---|---|---|---|
| **知识库** | 1 | 20 | 下数据、清洗、切句、抽样 | **Q1** |
| **检索** | **3**（1 人兼统筹） | 40 | 两种检索、合并、重排、界面、检索评测 | **Q2 + Q3** |
| **下游任务** | 2 | 40 | 弱标签、分类器、生成、RAG 评测、消融 | **Q4 + Q5** |

**标注那 1,000 句由三个人一起做**（可以跨组，见 `选题与标注方案.md`）。

> **不设独立的统筹岗**，也**不设报告组 / PPT 组**。
> 统筹（标注协调、周会、合稿、格式检查，约 8–10 h）由检索组某人兼任；
> 报告的五个 Question 和 slides 按上表归属，**谁做的谁写**，统筹只做拼装。
> 完整安排见 `docs/分工与任务清单.md` 第 9 节。

> **关于要不要在报告里写"谁做了什么"**：
> 作业说不写的话**全组共享同一个分数（这是作业推荐的做法）**，写了则按个人贡献分别打分。
> **建议共享分数**——随机分组的情况下，写明分工反而容易在最后阶段引发摩擦。

## 38. 可能会卡住的地方，以及怎么办

| 遇到 | 原因 | 怎么办 |
|---|---|---|
| `pip install` 各种报错 | Python 版本太老 | 确认 `python3 --version` ≥ 3.10 |
| spaCy 报 "Can't find model" | 忘了下模型 | `python -m spacy download en_core_web_sm` |
| 编码 30 万句跑了几小时还没完 | CPU 慢，正常 | 先只编码 5 万句验证流程；或者晚上挂着跑 |
| FAISS 装不上 | 装成了 `faiss` 而不是 `faiss-cpu` | `pip install faiss-cpu` |
| 训练时内存爆掉 | batch 太大 | 把 `per_device_train_batch_size` 改成 8 或 16 |
| 检索结果全是不相关的 | 索引和数据对不上 | 确认 `chunk_ids.npy` 的顺序和建索引时用的 df 完全一致 |
| Streamlit 每次查询都很慢 | 每次都重新加载模型 | 用 `@st.cache_resource` 缓存 model 和 index |

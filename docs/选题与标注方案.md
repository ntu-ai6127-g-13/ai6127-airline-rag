## 0. 结论

> ### 做「航空服务评价决策助手」
>
> 用 Skytrax 的 6.4 万条航司评论，做一个能回答**带约束的对比型问题**的系统：
>
> 「新加坡飞伦敦经济舱，哪家航司腿部空间评价最好？」
>
> 系统检索相关评论 → 分维度判断评价倾向 → 给出**带原文出处的对比结论**。

**为什么是它**：这是唯一一个**应用价值、技术难度、可落地性三者都成立**的选项。
下面第 2 节有完整对比。

## 1. 选题的七条标准

分两类。**第一类是门槛，不过就不能选；第二类决定能拿多少分。**

### 能不能做（硬门槛，一票否决）

| | 标准 | 具体要求 |
|---|---|---|
| **H1** | **数据量** | ≥10,000 篇文档、≥100,000 词。作业点名过"话题太冷门只找得到几百篇"这个失败模式 |
| **H2** | **数据平衡** | 作业原文：如果做情感分析而这个话题**只有负面评价，那就不是好题目** |
| **H3** | **标得动** | 要人工标 1,000 条且三人一致率 ≥80%。**标准必须客观到新手也能判** |
| **H4** | **数据拿得到** | 最好能直接下载。爬虫的反爬、限流、条款问题是最容易卡死新手的一环 |

### 值不值得做（决定分数）

| | 标准 | 为什么 |
|---|---|---|
| **V1** | **应用价值** | 作业明说要看"**useful and user-friendly**"——要做真有人会用的东西 |
| **V2** | **技术难度** | 也明说要看"**novelty and creativity**"。太简单的题拿不到高分 |
| **V3** | **撞车风险** | 与本年度或往年任何项目**重合 30% 即取消资格、记 0 分** |

> **V1 和 V2 与 H3、H4 是有张力的**——越有价值越难的题，往往越难落地。
> **选题就是在这条张力线上找平衡点，而不是往任何一端跑到底。**

### 为什么否掉 C（论文审稿）

它的**难度用错了地方**——难在标注，不难在方法。

- 审稿措辞高度对冲：*"The method is interesting but the evaluation on only two datasets limits the claims."* 这句算正面还是负面？**三个人会标出三个答案**，H3 直接不过
- 判断审稿人态度需要先看懂论文，新手成员会卡住
- 一条审稿 500–2000 词，切段是真问题，切不好检索质量直接崩

**它适合全员有 NLP 经验的组**，不适合我们。

### 其余否掉的

| 选项 | 卡在哪 |
|---|---|
| **Singlish 本地话题** | H4 不过。要自己爬 Reddit，有限流和条款风险，数据量和平衡都要现验证。**不该把项目押在"能不能爬到数据"上** |
| **Coursera 课程评论** | H2 不过。虽有 145 万条，但 **MOOC 评论绝大多数是 5 星**，正踩中作业警告的失败模式 |

| **ESG 漂绿检测** | H3 不过。"这段算不算漂绿"主观性太强，达不到 80% 一致率 |

## 3. 推荐方案详解

### 3.1 做一个什么产品

**不是**「航空评论情感分析」——那只是个练习。

**是**一个**帮人做出行决策的问答系统**，回答带约束、需要对比的真实问题：

```
「新加坡飞伦敦，经济舱，哪家航司腿部空间评价最好？」
「对比 Airline X 和 Airline Y 的餐饮和客舱服务」
「疫情之后，哪些航司的地勤服务明显变差了？」
```

**示例输出：**

```
查询：long haul economy legroom

按座位舒适度排序（仅长途经济舱评论，n=412）
┌──────────────┬─────────┬──────────────────────────────┐
│ 航司          │ 正面比例 │ 代表性原文                     │
├──────────────┼─────────┼──────────────────────────────┤
│ Airline X    │  68%    │ "plenty of legroom even at..." │
│ Airline Y    │  41%    │ "seat pitch acceptable but..." │
│ Airline Z    │  22%    │ "cramped, knees against the..." │
└──────────────┴─────────┴──────────────────────────────┘

其他维度参考：
  客舱服务  Airline Z 最高（74% 正面）
  性价比    Airline Y 最高（63% 正面）

⚠ 每条结论均可点开查看全部支撑原文
```

> **这就是「应用价值」的具体含义**：输出的不是一个情感分数，
> 而是**一个能直接用来做决定的、有据可查的对比结论**。

### 3.2 技术难度在哪（V2 怎么拿分）

这个题不是简单的分类任务。有四个真正有含量的点：

| # | 难点 | 为什么有难度 | 落地成本 |
|---|---|---|---|
| **1** | **对比型查询** | 单点问答只需检索一次；对比查询要**同时检索多个实体、再结构化对比**。这是明显更难的 RAG 形态 | 中 |
| **2** | **维度条件检索** | 「只检索关于座位的段落」要求索引本身是 **aspect-aware** 的，不能只按语义相似度捞 | 中 |
| **3** | **弱监督训练** ⭐ | 用 6.4 万条**自带的维度评分**当弱标签训练分类器，在自己标的 1,000 条**金标准**上评测。这是真实的研究范式（distant supervision），**写进报告很有分量** | **低**——标签已在 CSV 里 |
| **4** | **有据可查的推荐** | 输出必须附证据，可以直接用 faithfulness 指标验证——正好对上作业要求的 RAG 评测 | 低 |

> **第 3 点是这个选题的隐藏优势**：数据自带 6.4 万条弱标签，
> **让"弱监督 + 金标准评测"这个有分量的方法论几乎零成本就能做**。
> 大多数选题想做这个还得自己想办法造弱标签。

### 3.3 检索创新可以做什么（那 40 分）

数据自带的元数据直接支撑好几个作业列出的加分项：

| 创新点 | 怎么做 |
|---|---|
| **元数据筛选** | 按航司、舱位、航线、日期过滤 |
| **时间线检索** | 「只看 2023 年之后」——疫情前后对比 |
| **混合检索** | 关键词（BM25）+ 语义向量，用 RRF 融合 |
| **重排序** | 用 cross-encoder 对 top-100 重排 |
| **查询改写** | 「腿部空间」→ 扩展出 legroom / seat pitch / knee space |

## 4. 数据构成

### 4.1 数据源

| 数据集 | 规模 | 链接 |
|---|---|---|
| **Skytrax Airline Reviews**（建议用这个） | **81 家航司，64,440 条** | https://www.kaggle.com/datasets/efehandanisman/skytrax-airline-reviews |
| Airline Reviews | 类似规模 | https://www.kaggle.com/datasets/juhibhojani/airline-reviews |

| 原始爬取脚本（备用） | — | https://github.com/quankiquanki/skytrax-reviews-dataset |

### 4.2 每条评论有什么字段

| 类别 | 字段 | 用途 |
|---|---|---|
| **文本** | 评论正文 | ← 建索引和标注的主体 |
| **总体评分** | Overall Rating（1–10） | 抽样时控制正负比例 |
| **维度评分** ⭐ | Seat Comfort 座位舒适度 | 各 1–5 星，**乘客本人打的** |
| | Cabin Staff Service 客舱服务 | |
| | Food & Beverages 餐饮 | |
| | Inflight Entertainment 娱乐系统 | |
| | Ground Service 地勤服务 | |
| | Wifi & Connectivity 网络 | |
| | Value for Money 性价比 | |
| **元数据** | 航司、日期、舱位、航线、是否推荐 | 检索创新用 |

### 4.3 自带维度评分的三个用途

**七个评价维度是数据自带的，每个维度的分数由乘客本人打。** 这带来：

1. **不用自己定义维度**——省掉最容易吵起来的设计环节
2. **标注时有参照**——判"这句对座位是正面还是负面"时可对照乘客给座位打了几星，**一致率更容易达标**
3. **可以当弱标签**——6.4 万条免费的训练信号（见 3.2 第 3 点）

> ⚠️ **但这些评分不能直接当测试集标签交上去。**
> 作业要求测试集必须自己标。它们的作用是：抽样、辅助判断、有分歧时提供参照、做弱监督训练。

### 4.4 硬门槛核对

| 要求 | 满足情况 |
|---|---|
| ≥10,000 篇文档 | ✅ 64,440 条，超出 6 倍 |
| ≥100,000 词 | ✅ 每条平均 100+ 词，总量数百万 |
| 数据平衡 | ✅ 天然褒贬皆有；还能用 Overall Rating 精确控制抽样 |
| 测试集自己采集标注 | ✅ 从全量里抽 1,000 句自己标 |

## 5. 兜底方案：Steam 游戏差评归因

**只在候选 A 出问题时启用。**

### 5.1 数据源

| 数据集 | 规模 | 链接 |
|---|---|---|
| Steam Reviews（建议用这个） | **642 万条** | https://www.kaggle.com/datasets/andrewmvd/steam-reviews |
| 100 Million+ Steam Reviews | 1 亿条以上 | https://www.kaggle.com/datasets/kieranpoc/steam-reviews |
| Steam Games, Reviews and Rankings | 约 99 万条，含游戏信息 | https://www.kaggle.com/datasets/mohamedtarek01234/steam-games-reviews-and-rankings |

**字段**：评论正文、`review_score`（-1 / +1，玩家自己点的推荐或不推荐）、
`review_votes`（有用票数）、游玩时长、发布时间。

### 5.2 必须换角度做

**不要做**「游戏评论情感分析」——太泛，撞车风险极高。

**要做**「**从差评中抽取具体的、可修复的问题，生成给开发者的改进清单**」：

```
输入：某游戏名

输出：玩家反映的 Top 5 可修复问题
  1. 加载时间过长          提及 340 次   [查看原文]
  2. 某关卡难度曲线陡峭    提及 210 次   [查看原文]
  3. 多人模式匹配慢        提及 156 次   [查看原文]
  ...
（区分「可修复问题」与「主观口味差异」——后者不列入）
```

**这个角度的价值**：输出的是**可执行的行动项**而不是一个分数，
而且「区分可修复问题 vs 口味差异」本身是个有难度的判断，V1 和 V2 都能站住。

# 第二部分：标注方案

> **这是整个项目最重要、也最容易被低估的一步。**
> 评测集是衡量系统好坏的标尺——**标尺不准，后面所有指标都没有意义。**

## 6. 能不能让 AI 标

**不能全交给 AI。** 作业原文：

> "Build an evaluation dataset by **manually labeling** at least 1,000 records with an
> **inter-annotator agreement** of at least 80% (it is recommended to have **3 annotators**,
> but 2 is also OK)"

三个词是硬的：**manually（人工）**、**annotators（按人计数）**、**inter-annotator agreement（人与人之间的一致率）**。

**更实际的理由**：如果标签是 AI 打的，而下游分类器也用 AI，就成了「用 AI 评测 AI」——
**循环论证，下游那 40 分会整段失去意义**。而且同一个模型跑两遍的一致率接近 100%，
报上去等于告诉批改者我们没真标。

**✅ 可以做的：AI 预标 + 人工独立复核。** 标准做法，完全合规，见第 10 节。

---

## 7. 标什么

### 7.1 标注单元：句子

**把评论切成句子，逐句标。**

为什么不整条标：一条航空评论常常同时夸客舱服务、骂餐饮。
整条一个标签会丢信息，也支撑不了分维度分析。

> **操作**：用 NLTK 或 spaCy 切句，从中**随机抽 1,000 句**作为标注对象。
> 抽样时用 Overall Rating 分层，保证正负大致各半。

### 7.2 每句标三个字段

| 字段 | 取值 | 说明 |
|---|---|---|
| `subjectivity` | `objective` / `subjective` | 陈述事实 还是 表达观点 |
| `polarity` | `positive` / `negative` / `NA` | 只有 subjective 填；objective 填 `NA` |
| `aspect` | 见下表 | 这句在讲哪个方面 |

**`aspect` 取值（对齐数据自带的七个维度）**

| 值 | 中文 | 举例 |
|---|---|---|
| `seat` | 座位舒适度 | 腿部空间、椅背、宽度 |
| `staff` | 客舱服务 | 空乘态度、响应速度 |
| `food` | 餐饮 | 飞机餐、饮料 |
| `entertainment` | 娱乐系统 | 屏幕、片源 |
| `ground` | 地勤服务 | 值机、行李、登机口 |
| `wifi` | 网络 | 连接、速度、收费 |
| `value` | 性价比 | 票价是否值 |
| `overall` | 总体 | 泛指整段体验，不针对某一项 |
| `other` | 其他 | 与航空服务无关（如"我去参加婚礼"） |

## 8. 判定流程

**每句按这个顺序判，不要跳步：**

```
读一句话
  │
  ├─ 第 1 步：在讲航空服务吗？
  │     否 → aspect=other, subjectivity=objective, polarity=NA   【完成】
  │     是 → 继续
  │
  ├─ 第 2 步：陈述事实，还是表达感受/评价？
  │     纯事实 → subjectivity=objective, polarity=NA
  │              （aspect 仍要标）                                【完成】
  │     有评价 → subjectivity=subjective，继续
  │
  ├─ 第 3 步：正面还是负面？
  │     → polarity = positive / negative
  │
  └─ 第 4 步：主要在讲哪个方面？
        → aspect = seat / staff / food / ...                     【完成】
```

## 9. 边界情况裁定规则 ⭐

> **这一节决定能不能达到 80%。**
> 分歧几乎全部来自这些情况——**提前把规则定死，比事后吵架有效得多。**

| # | 情况 | 例句 | 裁定 |
|---|---|---|---|
| **R1** | 一句两个方面，褒贬不同 | *"The seat was comfortable but the food was terrible."* | **拆成两条**分别标：seat/positive、food/negative。拆不开时标**信息量更大**的那个 |
| **R2** | 事实陈述但明显含褒贬 | *"The flight was delayed 3 hours."* | **subjective / negative**。<br>判据：**这个事实在航旅语境里是否普遍被视为好或坏**。延误=负面，准点=正面 |
| **R3** | 中性事实 | *"I flew from Singapore to London in March."* | **objective**，polarity=NA |
| **R4** | 温和肯定 | *"The seat was okay / fine / acceptable."* | **positive**。"还行""可以"一律算正面，**不要算中性** |
| **R5** | 比较级 | *"Better than my last flight with X."* | **positive**（对本次而言） |
| **R6** | 假设/条件句 | *"If they had more legroom it would be great."* | **negative**——隐含"现在没有" |
| **R7** | 讽刺 | *"Wonderful, another 4-hour delay."* | **negative**，并**在 note 列标 `sarcasm`**（这批数据可当创新点素材） |
| **R8** | 建议/期望 | *"They should improve the meal options."* | **negative**——提改进建议意味着不满意 |
| **R9** | 提到多次飞行 | *"My outbound was great, the return was awful."* | **拆成两条** |
| **R10** | 泛泛整体评价 | *"Overall a great experience."* | subjective / positive / **aspect=overall** |
| **R11** | 无法判断 | 句子残缺、语义不明 | 标 `unclear` 并**丢弃**，从池子补一条新的。**不要硬猜** |
| **R12** | 提到价格但不评价 | *"The ticket was 800 SGD."* | **objective**。只有说"太贵了/很值"才算 value + subjective |

> **遇到表里没有的新情况**：不要各自决定。记下来，下次碰头统一裁定并**追加到这张表**，
> 然后回头修正已标的部分。

## 10. 标注流程

### Step 1 — AI 预标（1 人，1 小时）

把抽好的 1,000 句交给 LLM 按上述字段预标，生成带**建议标签**的表格。

> **提示词要点**：把第 7、8、9 节**原样贴进 prompt**，让 AI 按同一套标准预标，
> 人工复核时改动更少。

这只是省力，不是最终答案。**报告里要如实写明用了 AI 预标 + 人工复核。**

### Step 2 — 试标对齐（3 人，各 30 分钟）⭐ 不能跳

**三人独立标同样的 50 条**（不许商量），然后：

1. 算两两一致率
2. **逐条看所有不一致的地方**，问"我们为什么判得不一样"
3. 把新裁定**追加到第 9 节的表**
4. 不到 80% 就**再来一轮 50 条**

> **这是全流程最划算的投入。** 花 1 小时对齐标准，
> 比标完 1,000 条才发现不达标、全部重来，要省得多。

### Step 3 — 正式标注（3 人，各 1.5–2 小时）

**推荐：三人都标全部 1,000 条。** 一致率在全量上算，最扎实，挑不出毛病。
因为有 AI 预标，多数情况只需确认，每人 1.5–2 小时。

时间实在紧的退让方案：三人共同标 **200 条**用于算一致率，剩下 800 条分工各标一部分
——**但必须在报告里如实写明这个做法**。

**过程纪律：**

- ❌ 不要边标边讨论——那样一致率就没意义了
- ✅ 拿不准的**先按自己判断标下去**，同时记进"疑问清单"，之后统一处理
- ✅ 每标 200 条休息一下，疲劳会显著拉低质量

### Step 4 — 合并与仲裁（全组，1 小时）

| 情况 | 处理 |
|---|---|
| 三人一致 | 直接采纳 |
| 二比一 | **采纳多数** |
| 三人各不相同 | 现场讨论；讨论不出就**丢弃**并补一条新的 |
| 有人标 `unclear` | 丢弃并补充 |

## 11. 一致率怎么算

### 11.1 作业要求的指标

"agreement of at least 80%" 指**百分比一致率**：

```
一致率 = 两人标签相同的条数 ÷ 总条数
```

三人时算**两两一致率再取平均**（A-B、A-C、B-C 的均值）。

**按字段分别算**，难度不同：

| 字段 | 预期一致率 |
|---|---|
| `polarity` | 最容易，通常 85–95% |
| `aspect` | 中等，80–90% |
| `subjectivity` | **最难**，客观/主观界线最模糊 |

> `subjectivity` 上不去，说明 **R2 和 R3 的界线没讲清楚**，回去补规则。

### 11.2 建议额外报一个 Kappa

**百分比一致率有个缺陷**：如果 90% 的数据都是正面，两人闭眼全标正面也能得 90%。

**Cohen's Kappa（两人）/ Fleiss' Kappa（三人以上）** 会扣掉"碰巧一致"的部分：

| Kappa | 含义 |
|---|---|
| < 0.4 | 差 |
| 0.4 – 0.6 | 中等 |
| **0.6 – 0.8** | **良好**（目标区间） |
| > 0.8 | 非常好 |

```python
from sklearn.metrics import cohen_kappa_score
kappa = cohen_kappa_score(annotator_a, annotator_b)

from statsmodels.stats.inter_rater import fleiss_kappa   # 三人以上
```

**报告里两个都写**：百分比满足硬性要求，Kappa 体现方法严谨——**白送的加分**。

## 12. 文件格式

作业明确要求分类任务的评测集**必须叫 `eval.xls`**，且
**"use the same tabular format as the above-mentioned sentiment benchmarks"**
（对齐常见情感数据集的表格格式）。原文写明：**格式不对会扣分（demerit points）**。

### 降低格式风险的做法

常见情感 benchmark 的格式非常简单，基本就是 **`text` + `label` 两列**。
我们的标注有三个字段，比 benchmark 复杂。**保险的做法是把前两列做成 benchmark 的样子**：

| 列名 | 内容 | 例 | 说明 |
|---|---|---|---|
| **`text`** | 句子原文 | `The seat pitch was far too tight.` | ⭐ **第 1 列，对齐 benchmark** |
| **`label`** | `objective` / `positive` / `negative` | `negative` | ⭐ **第 2 列，单一标签列** |
| `id` | 唯一编号 | `0001` | 以下为补充信息 |
| `subjectivity` | `objective` / `subjective` | `subjective` | 拆开的两步标签 |
| `polarity` | `positive` / `negative` / `NA` | `negative` | |
| `aspect` | 见 7.2 | `seat` | |
| `review_id` | 来自哪条原始评论 | `R_48213` | |
| `airline` | 航司 | `Airline X` | |
| `cabin` | 舱位 | `Economy` | |
| `date` | 评论日期 | `2024-03-11` | |
| `label_a` `label_b` `label_c` | 三人各自的标注 | | 算一致率用 |
| `note` | 备注，如 `sarcasm` | | |

> **为什么这样排**：`label` 这一列把两步分类合并成一个三分类标签
> （客观 / 正面 / 负面），**任何按 benchmark 惯例读取的人或脚本都能直接用**。
> 后面的补充列不影响读取，但保留了我们全部的标注信息。
>
> **并且在报告里说明一句**："eval.xls follows the standard text/label tabular
> format of sentiment benchmarks; additional columns carry the two-step
> annotation and metadata." —— 主动说明格式，进一步降低被判"格式不对"的风险。

### 另外要满足的两条

作业在同一段还要求评测集：

- **不能有重复**（"make sure it does not contain duplicates"）——
  导出前跑一次 `df.drop_duplicates(subset=["text"])` 检查
- **尽量平衡**（"an equal number of positive and negative entries"）——
  抽样时就按总体评分分层取（见 §16）

> 另外单独存一份 `annotation_guideline.md`（即本文件第 7–9 节），
> **和数据一起放进提交的网盘压缩包**——体现标注是有规范的，不是随便标的。

## 13. 标注工具

```python
import streamlit as st, pandas as pd

df = pd.read_csv("to_label.csv")

st.caption(f"AI 预标建议：{df.loc[i, 'ai_suggestion']}")
st.caption(f"该乘客给此维度打分：{df.loc[i, 'aspect_rating']} / 5")   # 辅助参照

subj   = st.radio("客观还是主观", ["objective", "subjective"])

         ["seat","staff","food","entertainment","ground","wifi","value","overall","other"])

if st.button("保存并下一条"):
    # 写回 csv，自动记录标注人和时间戳
    ...
```

**好处**：一次只看一条不易看串行、自动记录谁标的和时间、导出即可算一致率。

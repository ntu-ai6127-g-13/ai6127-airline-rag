## 1. 三条硬规矩

**① 训练前排掉 `is_eval`。**

```python
train = df[~df.is_eval]          # 545,039 句
```

那 1,100 句是唯一一份信息源独立于评分的标签，混进训练集等于拿测试集训练。
**它不会报错**，指标只会变好看。详见[数据使用指南 §5.6](数据使用指南.md)。

**② 不要跑 `scripts/make_eval_set.py`。**

评测集已冻结——句子 id 和标注库里的人工标注绑死了。重抽会把 `E0001` 指向
另一句话，而所有按 id 的 join 照常成功、只是全错。脚本现在会拒绝覆盖，
别加 `--force` 绕过。要加句子用 `scripts/make_reserve.py`。

**③ 不要重建 `chunks.parquet` 之外的数据文件。** `data/eval/` 下的四个文件
和线上标注库是 1100/1100 严格对齐的，改任何一个都会让三个人已标的数据对不上号。

## 3. B 组 · 检索（40 分）

### 3.1 起点状态

`index/` 是空的，BM25 和 FAISS 都还没建过。`src/retriever.py`、`rerank.py`、
`generate.py` 都是占位文件。

### 3.2 已实测的数据特性（会影响你的设计）

| 事实 | 对你意味着什么 |
|---|---|
| 句子中位 **13 词**，P95 **33 词**，最长 270 词 | 短文本。嵌入不会被截断，但单句上下文少——检索命中后要取上下文窗口（[配方 §6.3](数据使用指南.md)） |
| 重复句 **21,102** 条，最高一句重复 **83 次** | 不去重会占满 top-K。**先取 top-100，去重后再截 top-20**，`dup_count` 留着做聚合加权 |
| 航司 **81 家，归一化后零重名** | 对比型查询的实体是干净的，不用做实体消歧 |
| 座位维度 **81 家全部 ≥30 条**，74 家 ≥100 条 | 分维度对比站得住，但**输出必须带 n**——样本量 30 和 300 的结论分量不一样 |
| 元数据覆盖：`date` 100% / `cabin` 97% / `route` 67% / `traveller_type` 65% | 按舱位筛是安全的；按航线或旅客类型筛会**悄悄丢掉三分之一数据**，筛完要报覆盖率 |
| 数据止于 **2019-06** | 做不了疫情前后对比。别在报告里写这个方向 |

### 3.3 推进顺序

1. **W1 基线**：BM25 + FAISS 各建一次，跑通单点查询。建索引前排掉
   `is_route_only` 和 `is_non_english`（[配方 §6.1](数据使用指南.md)）。
   **这一步就要把去重逻辑加进去**，后面再补会污染所有已有结果。
2. **W2 混合检索 + 重排**：RRF 融合，cross-encoder 重排 top-100。
3. **W3 对比型查询** ⭐ 这是拿分的核心。多实体同时检索 + 结构化对比输出。
4. **W4 aspect-aware 检索**：依赖 C 组的全库方面标签（见 §5 交接点）。
   C 组给不出来的兜底方案：用 `ASPECTS` 的关键词做过滤，报告里注明是
   规则基线而非分类器。
5. **W5 端到端 + faithfulness 指标**。

## 4. C 组 · 下游任务（40 分）

### 4.1 起点状态

`src/weak_labels.py`、`classify.py`、`evaluate.py` 都是 6 行占位文件。

### 4.2 弱标签的可用量（已排除评测集）

| | 评论级 | 句子级 |
|---|---|---|
| 合计 | **248,722** | **2,258,991** |

六个维度正例占比 43%–58%，基本平衡，不需要重采样。`ground` 偏负（43%）是
真实分布——延误投诉本来就多。

### 4.3 ⚠️ 已实测的噪声，开工前必须知道

拿三位标注员的试标数据实测（样本小，只能当粗略参考）：

| 指标 | 实测 | 含义 |
|---|---|---|
| 弱标签**极性**准确率 | **75%**（95%CI 61–85%，n=44） | 可用，但每 4 句错 1 句 |
| 关键词猜**方面**准确率 | **59%**（n=29） | 🔴 **短板** |
| 评分内部矛盾的评论 | **23.3%** | 覆盖 25.2% 的语料，同一句会同时被打上正负两种标签 |
| 一个评分复制给几句 | **8.9 句**（最长 102） | 真正讲该维度的通常只有 1–2 句 |

**噪声的根源**：评分是**整条评论**的，弱标签把它下放到了每一句。一条评论
`r_food=5`，它里面讲座位的句子也会被标成「餐饮正面」。

### 4.4 🔴 方面分类不能直接用关键词弱标签

整条 pipeline 是「先判方面 → 再取该维度评分当极性标签」。**方面错了极性必错。**
关键词基线只有 59%（八分类瞎猜是 12.5%，所以它有信号，但天花板太低）。

**建议方案：用高精度子集训练，牺牲召回换标签质量。**

规则：只保留「关键词**恰好命中一个**方面」且「**该维度评分是极端值**（4-5 或 1-2）」
的句子。实测产出：

```
139,086 句   正 65,041 / 负 74,045

  staff           45,850        food            21,451
  ground          24,503        value           13,572
  seat            23,229        entertainment   10,481
```

13.9 万条、六个方面都有足够样本、正负接近平衡。比起 2.26 M 条噪声标签，
这个更干净——**远程监督的标准做法就是拿精度换召回**，而且这个取舍本身
就是报告里 Q4 值得写的方法论内容。

对照实验建议直接做成报告的一张表：**全量弱标签 vs 高精度子集**，
在同一份金标准上比 P/R/F1。这比只报一个数字有分量得多。

### 4.5 推进顺序

1. **W1** `weak_labels.py`：把上面两套弱标签都构造出来（全量 + 高精度子集），
   存成 `data/processed/weak_labels.parquet`。**记得 `~is_eval`。**
2. **W2** `classify.py`：三个分类器（subjectivity / polarity / aspect）。
   先跑通，别调参。
3. **W3** 划一份 held-out 弱标签做临时验证集，两套标签做对照，调参。
   ⚠️ **临时验证集只能来自弱标签，绝不能碰那 1,100 句。**
4. **W4** 全库打标试跑（545,039 句），产出给 B 组的 aspect + polarity 列。
   这一步要估时间——54 万句过一遍分类器不是几分钟的事。
5. **W5** 冻结模型和超参。之后不许再改。
6. **W7** 金标准评测，写报告 Q4。

## 5. 两组的交接点

| 交接物 | 谁给谁 | 什么时候 | 给不出来的兜底 |
|---|---|---|---|
| 全库 aspect + polarity 标签 | C → B | **W4 末（10/15）** | B 组用关键词规则做 aspect 过滤，报告注明是规则基线 |

| 金标准 `eval.xls` | A → C | 10/25 仲裁后 | 无——这是硬依赖 |

**10/15 是 B 组最晚能等的时间。** 再晚，aspect-aware 检索就来不及做进报告。
C 组如果 W4 末给不出，当天就要通知 B 组走兜底方案，不要拖。

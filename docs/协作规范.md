# 协作规范

> 六个人同时改一个仓库，**不定规矩一定会互相覆盖**。
> 这份文件很短，**每个人开工前必须看一遍**。

---

## 1. 什么进 git，什么不进

**判断标准一句话：能用命令重建的，就不进 git。**

| 类型 | 进 git？ | 说明 |
|---|---|---|
| **代码** `src/` `scripts/` `app/` | ✅ **进** | |
| **文档** `docs/` `README.md` | ✅ **进** | |
| **实验记录** `experiments/log.md` | ✅ **进** | 报告全靠它 |
| **标注结果** `data/eval/` | ✅ **进** | 小且极重要，丢了要重标 3 小时 |
| **报告草稿与图表** `report/` | ✅ **进** | |
| 原始数据 `data/raw/` | ❌ 不进 | 23MB，`python scripts/download_data.py` 重建 |
| 处理后数据 `data/processed/` | ❌ 不进 | 几分钟重建 |
| 索引 `index/` | ❌ 不进 | 20 分钟重建 |
| 模型 `models/` | ❌ 不进 | 太大 |
| 虚拟环境 `.venv/` | ❌ **绝对不进** | **1.7 GB**，且每人环境不同 |

这些规则已经写进 `.gitignore`，**正常操作不会误传**。

> ⚠️ **唯一要小心的**：不要用 `git add -f` 强行添加被忽略的文件。
> 真需要共享大文件就发网盘。

## 2. 分支：每人一条，不要都往 main 推

**main 分支保持随时可用**。所有人在自己的分支上干活。

```bash
# 开工前，先从最新的 main 拉一条自己的分支
git checkout main
git pull
git checkout -b feat/retriever-bm25      # 名字见下面的规范

# 干活，随时提交
git add src/retriever.py
git commit -m "Add BM25 index building"

# 推到远端
git push -u origin feat/retriever-bm25
```

### 分支命名

```
feat/<模块>-<做什么>      新功能      feat/retriever-bm25
fix/<模块>-<修什么>       修 bug      fix/clean-mojibake
docs/<改什么>            改文档      docs/update-handbook
```

**按模块前缀分**，一眼看出是谁那块的：

| 小组 | 前缀 | 例子 |
|---|---|---|
| 知识库 | `feat/kb-` | `feat/kb-sentence-split` |
| 检索 | `feat/retriever-` `feat/rerank-` `feat/ui-` | `feat/retriever-hybrid` |
| 下游 | `feat/cls-` `feat/gen-` `feat/eval-` | `feat/cls-weak-labels` |
| 标注 | `feat/annot-` | `feat/annot-interface` |

## 3. 合并：开 Pull Request，别直接推 main

推完分支后，GitHub 会提示 **Compare & pull request**，点它。

**PR 描述写三句就够**：

```
做了什么：实现 BM25 检索和索引构建
怎么验证的：在抽样数据上搜 "legroom"，前 3 条都相关
需要注意：索引文件存在 index/bm25.pkl，不进 git
```

**谁来合并**：随便一个组员看一眼点 Merge 就行，**不用等 Xinghan**。
只有改到 `src/config.py` 或 `.gitignore` 这类全局文件时，才在群里说一声。

## 4. 每个人主要改哪些文件

**尽量只改自己那块，就不会冲突。**

| 小组 | 你的文件 |
|---|---|
| **知识库** | `src/build_kb.py`、`src/clean_text.py`、`scripts/make_sample.py` |
| **检索** | `src/retriever.py`、`src/rerank.py`、`app/streamlit_app.py` |
| **下游** | `src/weak_labels.py`、`src/classify.py`、`src/generate.py` |
| **评测** | `src/evaluate.py` |
| **所有人** | `experiments/log.md`、`docs/实验发现记录.md` ← 见下条 |

### ⚠️ 两个共用文件容易冲突

`experiments/log.md` 和 `docs/实验发现记录.md` **大家都会改**。

**减少冲突的办法**：

- **加在自己那一节的末尾**，不要动别人的内容
- **提交前先 `git pull`**
- 真冲突了也不难解决——**两边的内容都保留就行**，删掉 `<<<<<<<` 那几行标记

## 5. 每天/每次开工的固定动作

```bash
cd ~/Desktop/NLP
source .venv/bin/activate     # 激活环境（每开一个新终端都要）
git checkout main && git pull  # 拉最新
git checkout -b feat/xxx       # 开自己的分支
```

**收工前**：

```bash
git add <你改的文件>
git commit -m "说清楚做了什么"
git push
```

> **不要攒着一次推一大堆。** 做完一个小功能就推一次，
> 万一改坏了容易回退，别人也能早点看到进展。

## 6. 数据怎么同步

**不通过 git，各自本地重建**：

```bash
python scripts/download_data.py    # 下原始数据（一次就够）
python scripts/make_sample.py      # 生成开发用抽样
```

**只有一个例外**：**标注结果 `data/eval/` 要进 git**。
它体积小、且是人工标了几小时的成果，丢了没法重建。

## 7. 提交信息怎么写

**说清楚"做了什么"，不要写"更新"、"修改"、"提交"。**

```
✅ 好：Add BM25 index building and search
✅ 好：Fix mojibake in 42% of reviews (cp1252 double-encoding)
✅ 好：修正弱标签的关键词表，补充 6 个座位相关词

❌ 差：update
❌ 差：提交代码
❌ 差：fix bug
```

**为什么讲究这个**：万一后面要说明分工，git 历史是最直接的证据。
写清楚了，谁做了什么一目了然。

---

## 8. 遇到问题

| 情况 | 怎么办 |
|---|---|
| **卡住超过 3 天** | **必须在群里说。** 别自己憋——大概率别人 10 分钟就能解决 |
| 不小心推了大文件 | 别自己 force push，**先在群里说**，一起处理 |
| 合并冲突不会解 | 截图发群里 |
| 改坏了想退回 | `git checkout -- <文件>` 撤销未提交的修改 |

## 9. 检查自己的提交有没有算数

推完之后去看 **Contributors** 页面有没有自己：
https://github.com/RenXinghan/ai6127-airline-rag/graphs/contributors

**没有的话**说明 git 邮箱和 GitHub 账号对不上：

```bash
git config --global user.email "绑定GitHub账号的邮箱"
```

不确定用哪个邮箱？去 https://github.com/settings/emails 查。

> 这个坑我们已经踩过一次了——**四个提交全部显示"未关联"**，
> 是改写历史才修好的。人多了再发现就不好改了。

## 1. 三步拿到数据

数据文件**不在 git 里**（32 MB 的二进制，改一次就多存一份，仓库会迅速膨胀）。
它能用一条命令完整重建，所以每人本地生成一份：

```bash
git clone https://github.com/ntu-ai6127-g-13/ai6127-airline-rag.git
cd ai6127-airline-rag

python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m spacy download en_core_web_sm

python scripts/download_data.py     # 从 Kaggle 下原始数据（23 MB）
python -m src.build_kb              # 建库，约 14 分钟（spaCy 切句是大头）
python scripts/make_sample.py       # 可选：抽个小样本给开发用，几秒
```

### ⚠️ 跑之前先确认这两件，否则必报错

```bash
which python        # 必须指向 .../ai6127-airline-rag/.venv/bin/python
ls src/build_kb.py  # 必须存在
```

| 报错 | 原因 |
|---|---|
| `No module named 'src'` | **不在仓库根目录**。`python -m src.xxx` 只能在含 `src/` 的那一层跑，不能在 `~` 或别处 |
| `No module named 'pandas'` / 用的是 `/opt/homebrew/...python3.11` | **没 activate**。依赖装在 `.venv` 里，系统 Python 看不见。每开一个新终端都要 `source .venv/bin/activate` |

### ⚠️ 建完必须核对这一行 ⭐

`build_kb` 最后会打印：

```
is_eval：标出 1,100 句金标准（评测集 1,100 句）
```

**两个数必须相等。把这一行贴到群里。**

不相等 = 你这份语料的 `chunk_id` 和评测集**已经不是一套**。
原因几乎总是 spaCy 版本不对：必须 `spacy==3.8.16` **且**模型 `en_core_web_sm` 3.8.0。
切句器版本一变，句子边界就变，`chunk_id` 全线漂移。

```bash
python -c "import spacy, en_core_web_sm; print(spacy.__version__, en_core_web_sm.__version__)"
# 应输出：3.8.16 3.8.0
```

### ⚠️ 每次 `git pull` 之后也要查一次

`is_eval` 是**建库时烤进 parquet 的一列**，之后不会自己更新。
评测集扩充过（1,000 → 1,100，2026-09-17）——谁的 parquet 建于那之前，
`is_eval` 就只标了 1,000 句，剩下 100 句金标准会**静默进训练集**。
而 `build_kb` 的自检只在建库时跑，拉了新 meta 却没重建的人得不到任何提示。

三秒查清楚，不用重建 14 分钟：

```bash
python scripts/check_data.py
```

```
✅ 咬合正确，可以训练
   训练可用     545,039 句   →  df[~df.is_eval]
```

对不上会直接以退出码 1 退出并告诉你该怎么修。**开工前、每次 pull 之后各跑一次。**

> **为什么这一条值得单独拎出来**：脱钩之后 `df[~df.is_eval]` 会漏掉真正的金标准、
> 却排掉一批无辜的句子。训练集里因此混进人工标注的答案，P/R/F1 系统性虚高，
> **而且全程不报任何错**——等到写报告时发现，已经来不及重跑了。
> 核对这一行只要三秒。

跑完 `data/processed/` 里会有：

| 文件 | 规模 | 什么时候用 |
|---|---|---|
| `chunks.parquet` | 546,139 句 × 31 列 · 30 MB | **全组数据契约**，绝大多数时候用这个 |
| `reviews.parquet` | 61,167 条 × 17 列 · 14 MB | 需要整条评论级别的统计时 |
| `chunks_sample.parquet` | 2,519 句 × 31 列 · 0.2 MB | **开发阶段用这个**，几秒跑完，schema 与全量一致 |

> **开发时先用 sample。** 全量建一次索引要 20 分钟，每改一行代码都等这么久没法干活。
> sample 是从全量里按 `review_id` 抽的完整评论，schema 逐列一致（脚本里有 `assert` 保证），
> 代码写好后换个文件路径就能跑全量。

**建议自查**：跑完 `python scripts/test_env.py`，看到 `全部就绪 ✅` 说明环境没问题。

## 2. 两张表是什么关系

```
reviews.parquet          chunks.parquet
一行 = 一条评论    ──►    一行 = 一个句子
61,167 行                546,139 行（平均每条评论切 8.9 句）
```

同一条评论切出来的句子**共享同一个 `review_id`**，也共享全部元数据
（航司、舱位、日期、六个维度评分）——**变的只有 `text` 和 `sent_idx`**。

两张表用 `review_id` join（实测对得上，不多不少）：

```sql
SELECT * FROM 'data/processed/chunks.parquet' a
JOIN 'data/processed/reviews.parquet' b USING (review_id)
```

但**大多数情况下你不需要 join**——`chunks.parquet` 里已经带了 `review_text`
（父文档原文），检索按句子、展示按整条评论，一张表就够。

## 3. 31 列速查

| 列 | 类型 | 说明 |
|---|---|---|
| `chunk_id` | 文本 | 句子唯一编号 `R000000_s03`。**是标识符，不是排序键**（见 §5.1） |
| `review_id` | 文本 | 属于哪条评论 |
| `sent_idx` | 整数 | 句序。**排序用这个**。⚠️ 不连续（见 §5.1） |
| `text` | 文本 | **句子原文** ← 检索和分类都对它操作 |
| `review_text` | 文本 | 完整评论原文，展示证据时用 |
| `airline` | 文本 | 航司名（81 家） |
| `cabin` | 文本 | Economy / Premium Economy / Business / First |
| `traveller_type` | 文本 | Solo / Couple / Family Leisure / Business |
| `aircraft` | 文本 | 机型，如 `A380`（覆盖 32%，2,088 种） |
| `route` | 文本 | 航线原文 `Singapore to London via Dubai` |
| `route_from` | 文本 | **出发地**（已拆好，覆盖 67%） |
| `route_to` | 文本 | **目的地** |
| `route_via` | 文本 | 中转地 |
| `date` | 日期 | 评论日期（覆盖 100%） |
| `date_flown` | 日期 | 实际乘机月份（覆盖 65%，⚠️ **只有月精度**） |
| `overall_rating` | 数值 | 总体评分 1–10（⚠️ 读回来是 `float64`，见下方注） |
| `recommended` | 文本 | `yes` / `no` |
| `r_seat` `r_staff` `r_food` `r_entertainment` `r_ground` `r_value` | 数值 | 六个维度评分 1–5 ★ **弱标签来源**（同上，`float64`） |
| `n_sents` | 整数 | 这条评论一共留下几句 |
| `n_words` | 整数 | 这句有几个词 |
| `is_last` | 真假 | 是不是本条评论的末句（**总结句信号**，见 §6） |
| `is_route_only` | 真假 | 整句就是航线元数据（3.07%）。**建索引前排掉** |
| `dup_count` | 整数 | 这句在全语料出现几次。**检索后去重用** |
| `is_fragment` | 真假 | 是否以 `,;:!?)]` 开头的明显残片（19 句）。只标记，不删行 |
| `is_non_english` | 真假 | 是否为明显非英语句子（336 句）。**建索引前排掉**，只标记不删行 |
| `is_eval` | 真假 | 是不是人工金标准（1,100 句）。🔴 **训练前必须排掉**，见 §5.6 |

> 只有 **6 个维度评分，没有 wifi**。别照抄网上其他 Skytrax 数据集的字段名。

> ⚠️ **七个评分列读回来是 `float64`，不是整数。**
> `build_kb.py` 在内存里把它们转成了 `Int8`，但落盘走的是 DuckDB，
> 它不保留 pandas 的扩展 dtype，读回来就退化成 `float64` 了。
>
> 实际影响只有一条：**不要 `.astype(int)`**，评分是稀疏的，含 `NaN` 会抛
> `IntCastingNaNError`。比较和聚合完全不受影响，本文所有配方都是用
> `>= 4` / `<= 2` / `.notna()` 写的，照常工作：
>
> ```python
> (df.r_seat >= 4).sum()      # ✅  193,646（已排除评测集）
> df.r_seat.notna().sum()     # ✅  509,267
> df.r_seat.astype(int)       # 🔴  IntCastingNaNError
> ```
>
> 另外报告里出表时留意别把评分显示成 `7.0`。

## 4. 怎么读

### 4.1 只读需要的列 ⭐ 最重要的一条

```python
import pandas as pd

pd.read_parquet("data/processed/chunks.parquet")                      # 753 MB
pd.read_parquet("data/processed/chunks.parquet",
                columns=["chunk_id", "text", "airline"])              #  72 MB
```

**实测差 10 倍。** 大头是 `review_text`——父文档原文在每一句上都重复存了一份
（平均 8.9 遍）。你要是不做证据展示，就别读它。

### 4.2 大规模筛选用 DuckDB

```python
import duckdb
df = duckdb.sql("""
    SELECT airline, avg(r_seat) AS mean_seat, count(*) AS n
    FROM 'data/processed/chunks.parquet'
    WHERE route_from ILIKE '%Singapore%' AND route_to ILIKE '%London%'
      AND cabin = 'Economy Class' AND r_seat IS NOT NULL
    GROUP BY 1 ORDER BY 2 DESC
""").df()
```

DuckDB 直接查 parquet，**不用先读进内存**，54 万行毫秒级。
`pip install duckdb` 已在 `requirements.txt` 里。

## 5. ⚠️ 五个会让你算错的坑

### 5.1 `chunk_id` 不能用来排序

句序用 2 位补零，**超过 99 就变 3 位**（`_s100`），于是字典序乱掉——
`_s100` 会排在 `_s99` **前面**。实测 95 行受影响（1 条 124 句的长评论）。

```python
df.sort_values(["review_id", "sent_idx"])    # ✅
df.sort_values("chunk_id")                    # ❌ 长评论会乱序
```

```sql
ORDER BY review_id, sent_idx                  -- ✅
ORDER BY chunk_id                             -- ❌
```

### 5.2 `sent_idx` 有空洞，别拿它判断末句

碎片句（<3 词或 <5 字母）在切句时被丢掉了，所以 `sent_idx` 不连续，
**实测 11.5% 的评论有空洞**。

```python
df[df.is_last]                        # ✅
df[df.sent_idx == df.n_sents - 1]     # ❌ 会漏
```

保留 `sent_idx` 原样（不重新编号）是为了守住这个不变式（实测 0 条不一致）：

```
chunk_id == review_id + "_s" + f"{sent_idx:02d}"
```

### 5.3 报告里的数字，别用 `profile_data.py` 的

`scripts/profile_data.py` 报的是**切句之前**的中间值。两组数字都对，
但描述的不是同一个东西，混用会让报告里的数字对不上。

| | 切句前（profile_data） | **最终知识库（用这个）** |
|---|---|---|
| 文档数 | 61,172 | **61,167** |
| 总词数 | 8,402,547 | **8,276,082** |
| 句子数 | — | **546,139** |
| 不重复词 type | — | **130,385** |

以 `python -m src.build_kb` 的输出为准。脚本里已经加了提醒。

### 5.4 维度评分是**稀疏**的

| 维度 | 有评分的句子 | 覆盖率 |
|---|---|---|
| value | 533,423 | 98% |
| staff / seat | ~510,000 | 93% |
| food | 438,592 | 80% |
| entertainment | 370,883 | 68% |
| **ground** | **354,331** | **65%** |

**entertainment 和 ground 的训练数据明显少。** 如果这两类分类效果偏弱，
那是数据量的问题不是模型的问题——这是一个有依据的分析，值得写进报告 Q4。

### 5.5 重复句会挤占检索结果

**21,102 句（3.86%）在语料里不是唯一的**，最高的一句出现 83 次。

在真实 BM25 上实测：查 `"food was good"`，**top-20 的 20 个位置全是同一句**
`"Food was good."`；查 `"worst airline ever"`，20 个位置只有 2 个不同句子。
**五个查询平均，top-20 只有 6.4 个不同句子。**

但**不要直接删**——`"All flights were on time."` 出现 34 次、横跨 15 家航司，
**这个「34」本身就是聚合证据**。正确做法见 §6.2。

---

### 5.6 🔴 训练集必须排掉 `is_eval`

训练信号全部来自远程监督（乘客自己打的维度评分）。那 1,100 句人工标注是
**唯一一份信息源独立于评分的标签** —— 它一旦混进训练集，等于拿测试集训练：

```
人工金标准  ←信息源独立→  可信的评测
人工金标准  ←混进训练集→  P/R/F1 系统性虚高，且无法在报告里辩护
```

**最糟的是它不会报错。** 指标会变好看，没有任何异常可查。

```python
train = df[~df.is_eval]          # 545,039 句
```

想更严格：同 992 条评论里还有约 1 万句非金标准的句子，它们和金标准**共享
同一套评分**，属于更弱的关联泄漏。按 review 级隔离：

```python
eval_reviews = set(pd.read_csv('data/eval/to_label_meta.csv').review_id)
train = df[~df.review_id.isin(eval_reviews)]      # 533,236 句
```

⚠️ `is_eval` 由 `src/build_kb.py` 在建库时计算。**如果你的 `chunks.parquet`
是 2026-09-17 之前生成的，它没有这一列** —— 重新跑一次 `python -m src.build_kb`。

## 6. 各组的常用配方

### 6.1 B 检索组：建索引前排掉噪声

```python
import pandas as pd
df = pd.read_parquet("data/processed/chunks.parquet",
                     columns=["chunk_id", "text", "is_route_only",
                              "is_non_english", "dup_count"])
index_pool = df[~df.is_route_only & ~df.is_non_english]  # 546,139 → 529,031 句
```

其中 16,772 句是 `"Guangzhou to New York."` 这种纯航线元数据，
和 `route` 列 100% 重复、没有情感极性；另有 336 句明显非英语内容。
两类都只在数据中打标记，由使用方在建索引时排除。

### 6.2 B 检索组：检索后去重，但保留权重

```python
# 先取 top-100 候选，去重后再截 top-20
dedup = candidates.drop_duplicates(subset=["text"]).head(20)
# dup_count 留着做聚合加权 —— 出现 34 次说明 34 条评论都这么说
```

**展示时去重、聚合时用 `dup_count` 加权。** 这是 §5.5 那个矛盾的解法，
也是报告 Q3「检索创新」的一个现成素材。

### 6.3 取一句的上下文窗口

有了 `sent_idx`，一个窗口函数就够，不用解析 `chunk_id` 字符串：

```sql
SELECT chunk_id,
       lag(text)  OVER w AS prev_sent,
       text                AS this_sent,
       lead(text) OVER w AS next_sent
FROM 'data/processed/chunks.parquet'
WINDOW w AS (PARTITION BY review_id ORDER BY sent_idx)
QUALIFY chunk_id = 'R000000_s03'
```

### 6.4 C 下游组：从评分造弱标签

```sql
SELECT count(*) FILTER (WHERE r_seat >= 4) AS pos,
       count(*) FILTER (WHERE r_seat <= 2) AS neg,
       count(*) FILTER (WHERE r_seat = 3)  AS discard
FROM 'data/processed/chunks.parquet'
WHERE r_seat IS NOT NULL
  AND NOT is_route_only
  AND NOT is_non_english
```

实测 seat 维度：**正 188,806 / 负 201,822 / 丢弃 103,772**。

🔴 **上面这条 SQL 缺一个条件。正确写法要加 `AND NOT is_eval`：**

```sql
WHERE r_seat IS NOT NULL AND NOT is_route_only AND NOT is_eval
```

⚠️ **弱标签只能用来训练，绝不能用来评测。** 评测用 `data/eval/` 里的人工金标准。
两者混了，报告 Q4 的 P/R/F1 就没有意义了 —— 而且**不会报任何错**，见 §5.6。

### 6.5 标注组：标完之后怎么合

```sql
SELECT * FROM 'data/eval/to_label.csv' a
JOIN 'data/eval/to_label_meta.csv' b USING (id)
```

标注文件里**故意不含**航司和评分——标注员看到评分会被锚定，
金标准就和弱标签相关了。详见 `data/eval/README.md`。

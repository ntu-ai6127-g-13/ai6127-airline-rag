# 句子向量分类器（独立实验，不替换原系统）

本目录是 `main` 之上的纯新增实验。原 `src/`、`app/`、默认标签索引构建流程均不修改；
切换到这个分支后，原系统仍按原方式运行，只有显式执行本目录命令才会用到这里的模型。

该方案尚未通过独立验收，不是正式替代版本。本文件不展示任何具体评测句子的原文或逐条标签，
只给聚合后的分数。

## 动机

对线上实际在用的分类器（`eight-aspect-subjectivity-polarity-v4.1`，TF-IDF + 逻辑回归）做
方面混淆矩阵审计，发现两个具体问题：

1. 有两个方面类别的准确率明显低于其余类别（60-90 个百分点的差距），其中一个几乎均匀地被
   误判到其它各个类别。
2. 客观句召回率只有个位数百分比：模型几乎把任何提到方面关键词的句子都判成主观，即使那句话
   只是平铺直叙地陈述事实。
3. 两个服务人员相关的方面之间互相混淆的次数明显偏高，尽管弱标签规则（`src/weak_label_rules.py`）
   已经用否定前瞻显式区分了对应的两种常见写法。

这些都是词袋特征（TF-IDF）本身的局限：它只统计词出现与否，不编码词序和上下文。本实验换一个
变量——把 `TfidfVectorizer` 换成冻结的 `all-MiniLM-L6-v2` 句子向量（或者两者拼接），其余全部
复用生产代码（`src/classification_pipeline.py` 的弱标签生成、父评论切分、训练/验证边界检查），
验证这个变量能不能缓解上述问题。

## 评测方式说明

训练只用弱标签（远程监督），训练入口会触发 `src.training_isolation` 的拦截，不读取任何独立
人工标注的答案。效果判定用了两套跟训练数据完全无关的评测:

1. 项目现有的一份独立人工标注记录（通过 `src.gold_release` 读取，训练代码不会接触它）。
2. 另抽取 200 句、不在第 1 套记录里出现过的真实评论句子，单独标注主客观/方面/情感，作为
   第二套检验。抽样时特意多采了一些两个服务人员相关方面容易混淆的句子，以便继续检验上面
   第 3 点动机，其余为随机抽样。

**只有同时在两套评测上都复现的改善，才认为是真实、可能泛化的提升**；只在其中一套上出现、
另一套上消失或反转的部分，判定为对那一套具体数据的拟合，不计入结论。这是因为开发过程里先用
第 1 套评测发现了 TF-IDF 的缺陷、又针对缺陷设计方案、再回去用同一套评测确认方案有效——这个
闭环本身降低了结论的独立性，第 2 套评测是用来部分弥补这一点的交叉检验，但样本量仍偏小、
且是单次运行标注，不是多人标注取一致性结果。

## 方法

- 复用 `src.classification_pipeline.checked_input` / `build_labels` / `split_labels`：
  弱标签生成规则、训练/验证按父评论切分、评测句排除逻辑完全不变。
- 两种特征模式，由 `train.py --features` 选择：
  - `embedding`：`fit_models`（TF-IDF + 逻辑回归）替换为冻结 `all-MiniLM-L6-v2` 编码 +
    逻辑回归。
  - `combined`：TF-IDF 稀疏矩阵与 MiniLM 稠密向量横向拼接（`scipy.sparse.hstack`）后，训练
    同一个逻辑回归；两种特征间没有人工设定的混合权重，系数由训练过程自己学出。
- 两种模式都用 `class_weight='balanced'`，与生产基线一致。
- 评测口径：`src.quality.classification_metrics`，在主观句上算方面/情感宏 F1、联合正确率，
  在全部句子上算主观召回率和客观召回率。

## 结果

### 弱标签验证集（已知对看起来“精确”的特征有利，不是最终判据）

| 任务 | TF-IDF（生产基线） | MiniLM 向量 | TF-IDF+MiniLM 拼接 |
|---|---:|---:|---:|
| aspect macro-F1 | 0.9917 | 0.9261 | 0.9864 |
| subjectivity macro-F1 | 0.8040 | 0.7479 | **0.8527** |
| polarity macro-F1 | 0.9483 | 0.9268 | 0.9490 |

**这组数字不能直接当作能力排名**：弱标签验证集里“客观”类别的样本只有约 40 条（相对“主观”类
数万条，严重失衡），而且几乎全部来自“这句话不含任何方面关键词”这一条规则——例如纯粹的航线
描述（“从 A 飞到 B，经停 C”这种模板句）。这类句子不需要任何语义理解，只要检测“有没有命中方面
关键词”就能几乎完美分类，三种特征在这批样本上都能接近满分，测不出真实差异。真正有区分力的
是下面独立于训练数据的两套检验。

### 第一套检验（项目既有的独立人工标注记录；只给聚合分数）

| 指标 | 目标 | TF-IDF（生产基线） | MiniLM 向量 | TF-IDF+MiniLM 拼接 |
|---|---:|---:|---:|---:|
| 方面 macro-F1 | 85% | 0.6111 | 0.6761 | **0.6796** |
| 情感 macro-F1 | 90% | 0.8207 | 0.8295 | **0.8518** |
| 联合正确率 | 80% | 0.5615 | 0.5930 | **0.6126** |
| 主观召回率 | 97% | 0.9989 | 0.9967 | **1.0000** |
| 客观召回率 | （无正式目标，诊断用）| 0.0741 | **0.3827** | 0.2099 |

四项正式目标在三种特征下都未达标。

### 第二套检验（独立抽样 200 句，与第一套无重叠）

| 指标 | TF-IDF（生产基线） | MiniLM 向量 | TF-IDF+MiniLM 拼接 |
|---|---:|---:|---:|
| 方面 macro-F1 | 0.6176 | 0.6179 | **0.6561** |
| 情感 macro-F1 | 0.8414 | 0.8716 | **0.8775** |
| 联合正确率 | 0.5588 | 0.5647 | **0.6059** |
| 主观召回率 | 1.0000 | 0.9824 | **1.0000** |
| 客观召回率 | 0.0000 | **0.2667** | 0.1333 |

### 两套检验放在一起看，哪些改善是真的

- **客观召回率的提升是唯一在两套检验上都大幅、一致出现的改善**（第一套 7.4%→38.3%，第二套
  0%→26.7%，拼接方案介于两者之间）。判定为真实。
- **方面 macro-F1 / 联合正确率**：第一套检验上看到的改善（embedding 方案 +6.5/+3.2 个百分点）
  在第二套上大幅缩小（+0.03/+0.6 个百分点）；在更早一轮只有 70 句的第二套抽样里，这两项甚至
  反转（TF-IDF 更高）。样本量从 70 加到 200 后方向重新转为正向，说明 70 句时的反转主要是小
  样本噪声，但第一套检验上 +6.5/+3.2 个百分点的具体数值本身被判定为拟合，不能直接采信；两套
  检验上，**拼接方案**（combined）在这两项上的改善比单纯 embedding 更大、更一致，是当前三者
  里最稳健的选择。
- **情感 macro-F1**：两套检验方向一致为正（拼接方案分别 +3.1/+3.6 个百分点），判定为有改善
  趋势，但样本量仍偏小。
- **主观召回率**：两套检验、三种特征下都在 97-100% 区间内小幅波动，拼接方案在两套检验上都
  达到 100%，没有观察到有意义的代价。

### 三种特征方案的取舍

拼接方案（combined）在两套检验上，方面 F1、情感 F1、联合正确率、主观召回率四项都是三者中
最高或并列最高，客观召回率介于 TF-IDF 和纯 embedding 之间（比 TF-IDF 好得多，比纯 embedding
保守）。纯 embedding 方案客观召回率最高，但其余四项不如拼接方案。如果只能选一个方向替换生产
基线，拼接方案目前证据更充分；如果目标明确是“优先解决客观句误判”这一个具体问题，纯
embedding 方案在这一项上领先更多。

## 与另一个实验分支（`feat/example-assisted-classifier`）的区别

那个分支也用到了 MiniLM 和 TF-IDF，但用途不同：它用 `0.7 × MiniLM 余弦 + 0.3 × TF-IDF 余弦`
的固定加权分数去检索最相似的参考示例，再把示例作为 few-shot 上下文交给冻结的 Qwen3-4B 做分类
推理——最终下判断的是大模型，MiniLM/TF-IDF 只负责挑例子，混合权重是人工定的常数。

本实验里，MiniLM/TF-IDF 是直接拼接成分类特征，喂给一个训练出来的逻辑回归，模型自己从数据里
学出每一维特征的权重，不涉及大模型推理，预测是纯矩阵运算（毫秒级，可以批量跑全库）。两个分支
技术路线不同，评测数据也不同（那个分支用的是未提交到 Git 的 AI 标注句子），不构成互相验证。

## 复现

```bash
# 训练 embedding 方案（约10分钟：编码29万句 + 训练三个逻辑回归）
.venv/bin/python -m experiments.embedding_classifier.train \
    --output-dir outputs/embedding_classifier_run1 --features embedding

# 训练拼接方案（同样约10分钟，多了一次TF-IDF拟合，耗时增加很少）
.venv/bin/python -m experiments.embedding_classifier.train \
    --output-dir outputs/combined_classifier_run1 --features combined

# 跑第一套检验（只输出聚合分数，不打印原文）
.venv/bin/python -m experiments.embedding_classifier.evaluate_held_out \
    --model outputs/embedding_classifier_run1/model.joblib
.venv/bin/python -m experiments.embedding_classifier.evaluate_held_out \
    --model outputs/combined_classifier_run1/model.joblib
```

第二套 200 句检验的原文和标注未纳入本仓库（单次运行标注、未经多人校验，不适合当作可复用的
评测资产），对应评测代码也因此未包含在本目录；上面“第二套检验”表格里的数字来自本次运行记录。

## 边界与局限

- 没有修改生产标签索引构建流程（`src/label_index.py`）、查询服务默认行为或默认依赖；
  需要显式调用本目录脚本才会用到这里训练的模型。
- 训练/评测使用的弱标签生成、父评论切分、评测句排除逻辑与生产基线完全一致，复用
  `src.classification_pipeline` 中的函数，不是另外重新实现的一套。
- 没有调参或挑选模型；本实验每种特征模式只跑了一组固定配置（`class_weight='balanced'`，
  `max_iter=1000`，`seed=42`）。
- 没有做权重微调；`all-MiniLM-L6-v2` 全程冻结，只当特征提取器用。
- 见上面“评测方式说明”：第一套检验既用于诊断也用于验证，独立性有限；第二套检验缓解但没有
  完全解决这个问题，且样本量仍偏小、单次运行标注。
- 全量 529,031 句离线标签索引重建所需时间未实测；如果要接入生产，需要先确认全量编码+预测的
  耗时和内存开销。
- 两个服务人员相关方面之间的混淆没有解决，仍需要单独诊断。
- 本实验由同一人在本机单次运行完成，没有独立复核。
